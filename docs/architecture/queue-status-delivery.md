# Queue 상태 전달: Polling에서 Push로 가야 하는 이유

## 문제

부하테스트(오픈런 burst, ~9천 명 유입) 중 대기열이 특정 지점에서 정체되는 걸 관측했다. 원인 추적 결과:

```yaml
tomcat.threads.busy = 200
tomcat.threads.current = 200 (max와 동일, 완전 포화)
```

`GET /queue/me` 폴링(1초 간격, 대기 인원 수만큼 발생)이 Tomcat 스레드 풀을 전부 점유했고, 점유율을 낮춰야 할 `leave()` 요청도 같은 풀에서 순서를 기다리게 됐다. `leave()`가 지연되니 occupancy가 안 줄고, admission scheduler는 매번 `room=0`으로 판단해 아무도 admit하지 않는다. 폴링 트래픽이 자기 처리를 굶기는 구조다. 신규 로그인 요청까지 타임아웃날 정도로 스레드 풀 전체가 마비됐다.

## 왜 스레드 풀 증설로는 부족한가

폴링 트래픽의 크기가 대기 인원(백로그) 크기에 비례해서 계속 커진다. 스레드 풀을 200에서 800으로 올리면 지금 규모는 버티지만, MVP(10만)·Target(100만) 티어로 갈수록 같은 포화가 재발한다. **"물통을 키우는 것"**이지 **"물이 계속 불어나는 원인"**을 안 건드린다.

## 근본 원인과 방향

클라이언트가 상태 변화를 알아내는 유일한 방법이 "주기적으로 물어보는 것"이라는 데 있다. 서버가 상태 변화 시점에 직접 알려주는 방식(push)으로 바꾸면, 트래픽 크기가 백로그 크기가 아니라 **상태 변화 빈도**에 비례하게 된다.

**WebSocket vs SSE**: 이 용도(서버→클라이언트 단방향, 클라이언트→서버는 이미 REST로 처리 중)엔 SSE가 더 맞다. 재연결을 브라우저(`EventSource`)가 자동으로 처리해주고, 순수 HTTP라 인프라(프록시/LB)에 더 잘 얹힌다. WebSocket은 ADMITTED 이후 좌석 동기화 단계(README에 이미 계획됨)에 남겨두고, **admit이라는 도메인 전환점을 프로토콜 전환점으로 삼는다** — 대기 중엔 SSE, 입장하면 WS.

## 계획

1. enter() — 성공/실패만 (command/query 분리 원칙 유지)
2. queue/me — 최초 정확한 등수. 재연결 시에도 다시 거침(=재동기화)
3. SSE 연결 (/performances/{id}/queue/stream, performance 단위)
서버: admission scheduler tick에서 admit된 인원 > 0일 때만
"N명 처리됨"을 그 performance 대기자 전원에게 broadcast
(0명 처리된 tick은 아무것도 안 보냄 → 막힌 구간엔 트래픽 0)
4. 클라이언트: 3을 받을 때마다 로컬 등수 -= N
(admit()이 항상 대기열 맨 앞부터 pop하는 FIFO라 이 로컬 계산이
서버 재계산과 수학적으로 동일함 — 근사치가 아니라 정확한 값)
내가 admit되는 tick:
5. 서버: 그 memberId 연결에만 개별로 ADMIT + admissionToken 전송
→ 보내자마자 서버가 그 SSE 연결 먼저 close (클라이언트의 정상
종료에 기대지 않음, leave() TTL 논의와 같은 원칙)
(broadcast(3)와 개별 전송(5)은 같은 tick에 같이 일어나되 별개 메시지:
하나는 공개 정보(등수 변화), 하나는 개인 정보(토큰))
6. 클라이언트: ADMIT 수신 → admissionToken 확보 → 페이지 이동 → /goal 호출

## 남는 비용 — broadcast fan-out 자체

빈도(얼마나 자주 보내는가)는 이 설계로 확실히 줄지만, **한 번의 broadcast를 N개 연결에 실제로 밀어넣는 비용은 여전히 N에 비례한다.** 스케줄러 스레드(기본 1개)가 이 fan-out을 직접, 순차적으로 하면 N이 커질 때(Target~Stretch 티어) 그 스레드 자체가 막혀 다음 tick이 밀리는, 지금과 유사한 종류의 문제가 다른 자리에서 재발할 수 있다. README에 이미 계획된 Redis Pub/Sub backplane(원래 좌석 동기화용)을 재사용해 인스턴스 간 분산 + 인스턴스 내 병렬 fan-out으로 완화한다 — 이 프로젝트가 이미 필요로 하게 될 인프라이므로 새로운 부담이 아니라 기존 계획의 확장이다. Smoke~MVP 규모에서는 단일 인스턴스 병렬 fan-out만으로 충분하므로, Pub/Sub 연동은 최초 구현 스코프에서 제외하고 Target 티어 진입 시점의 후속 작업으로 남긴다.
